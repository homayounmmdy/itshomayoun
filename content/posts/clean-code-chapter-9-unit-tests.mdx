# تست‌های واحد؛ نگهبانان کیفیت کد

فصل نهم کتاب **Clean Code** یک پیام بسیار واضح دارد: **کد تست، شهروند درجه دو نیست.** تست‌های کثیف به سرعت به یک بدهی فنی تبدیل می‌شوند، دور ریخته می‌شوند و در نهایت باعث فاسد شدن کد اصلی می‌شوند. تست‌های تمیز، با حذف «ترس از تغییر»، تمام ویژگی‌های خوب نرم‌افزار (انعطاف‌پذیری، نگهداری‌پذیری و...) را ممکن می‌سازند.

در ادامه، مهم‌ترین اصول تست‌نویسی حرفه‌ای از دیدگاه رابرت مارتین را مرور می‌کنیم.

## ۱. قوانین سه‌گانه TDD (Test-Driven Development)
1. قبل از نوشتن هرگونه کد اصلی (Production Code)، یک تست واحدِ شکست‌خورده بنویسید.
2. بیش از حدِ نیاز برای شکست خوردن تست، کدِ تست ننویسید (حتی شکست کامپایل، یک شکست محسوب می‌شود).
3. بیش از حدِ نیاز برای پاس شدن آن تستِ شکست‌خورده، کد اصلی ننویسید.

## ۲. اصول کلیدی تست‌نویسی تمیز
* **خوانایی پادشاه است:** تست‌ها باید شفاف، ساده و فشرده باشند. بهترین الگو، **Build-Operate-Check** است: داده‌ها را بسازید (Build)، روی آن‌ها عملیات انجام دهید (Operate) و نتیجه را بررسی کنید (Check).
* **زبان تست مختص دامنه (Domain-Specific Testing Language):** توابع کمکی بسازید تا جزئیات تکراری و پیچیده (Boilerplate) پنهان شوند. این کار باعث می‌شود تست‌ها مثل یک API تخصصی و گویا خوانده شوند.
* **یک مفهوم، حداقل Assert:** در هر تابع تست، دقیقاً **یک مفهوم** را بررسی کنید. هدف نهایی این است که در هر تست فقط **یک `assert`** داشته باشید تا نتیجه‌گیری کاملاً شفاف و بدون ابهام باشد.
* **استاندارد دوگانه (Dual Standard):** کد تست نیاز به بهینه‌سازی شدید برای CPU یا حافظه (مانند کد اصلی) ندارد، اما **باید** از نظر خوانایی و ساختار، کاملاً تمیز باشد.

## ۳. اصول F.I.R.S.T. برای تست‌های عالی
یک تست واحد خوب باید ۵ ویژگی زیر را داشته باشد:
* 🚀 **F**ast (سریع): باید به‌سرعت اجرا شوند تا توسعه‌دهندگان تشویق به اجرای مکرر آن‌ها شوند.
* 🔗 **I**ndependent (مستقل): نباید وضعیت (State) مشترک داشته باشند؛ تست‌ها باید در **هر ترتیبی** قابل اجرا باشند.
* 🔄 **R**epeatable (تکرارپذیر): در هر محیطی (بدون نیاز به شبکه، دیتابیس خارجی یا شرایط خاص) به درستی کار کنند.
* ✅ **S**elf-Validating (خود-اعتبارسنج): خروجی بولین واضح (Pass/Fail) داشته باشند و نیازی به بررسی دستی لاگ‌ها نباشد.
* ⏱️ **T**imely (به‌موقع): درست قبل از کد اصلی که قرار است تست کنند، نوشته شوند.

## مثال‌های کد (JavaScript)

```javascript
// ❌ بد: تست کثیف، چندین مفهوم، بدون زبان مختص دامنه، سخت برای خواندن
test('user registration flow', () => {
  const db = new Database();       // جزئیات غیرضروری راه‌اندازی
  db.connect();
  const user = new User('john', '123');
  db.save(user);
  
  const result = db.query('SELECT * FROM users WHERE name="john"');
  expect(result.length).toBe(1);             // Assert 1
  expect(result[0].password).toBe('123');    // Assert 2
  expect(db.isConnected()).toBe(true);       // Assert 3 (بررسی یک مفهوم کاملاً متفاوت!)
});


// ✅ تمیز: مطابق با اصول F.I.R.S.T.، استفاده از زبان مختص دامنه، الگوی Build-Operate-Check

// ۱. زبان مختص دامنه (پنهان کردن جزئیات تکراری در توابع کمکی)
function registerTestUser(name, password) { /* ... */ }
function getTestUser(name) { /* ... */ }

// ۲. تک‌مفهومی، خود-اعتبارسنج و مستقل
test('registered user password is saved correctly', () => {
  // BUILD (ساخت)
  const testName = 'john';
  const testPassword = '123';
  
  // OPERATE (عملیات)
  registerTestUser(testName, testPassword);
  
  // CHECK (بررسی - یک مفهوم واضح با یک assertion)
  const savedUser = getTestUser(testName);
  expect(savedUser.password).toBe(testPassword);
});
```
