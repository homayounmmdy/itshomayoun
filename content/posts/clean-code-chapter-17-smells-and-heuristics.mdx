# بوها و نشانه‌های هشداردهنده؛ چگونه کد بد را تشخیص دهیم؟

فصل هفدهم کتاب **Clean Code** به عنوان یک چک‌لیست جامع و عملی عمل می‌کند. رابرت مارتین در این فصل، «بوهای بد کد» (Code Smells) و نشانه‌های هشداردهنده‌ای را فهرست می‌کند که نشان‌دهنده طراحی ضعیف هستند. شناخت این نشانه‌ها به ما کمک می‌کند تا قبل از تبدیل شدن کد به یک آشوب غیرقابل نگهداری، آن‌ها را شناسایی و رفع کنیم.

در ادامه، مهم‌ترین دسته‌بندی‌های این نشانه‌ها را مرور می‌کنیم.

## ۱. نظافت و توابع (Comments & Functions)
* **حذف زوائد:** کدهای کامنت‌شده، کدهای مرده (Dead Code) و کامنت‌های تکراری را بی‌رحمانه حذف کنید. کامنت‌ها نباید حاوی متادیتا باشند (این وظیفه سیستم کنترل نسخه مثل Git است).
* **محدودیت آرگومان‌ها:** تعداد آرگومان‌ها را به ۰ تا ۳ محدود کنید. از **آرگومان‌های پرچمی** (Flag Arguments) و آرگومان‌های خروجی (Output Arguments) به‌شدت پرهیز کنید.
* **یک کار، یک سطح:** هر تابع باید دقیقاً **یک کار** را انجام دهد و در **یک سطح از انتزاع** باقی بماند. برای شفاف‌سازی منطق پیچیده، از متغیرهای توضیحی (Explanatory Variables) استفاده کنید.

## ۲. طراحی و ساختار (Design & Structure)
* **پلی‌مورفیسم به جای شرط:** زنجیره‌های طولانی `switch` یا `if-else` را با پلی‌مورفیسم جایگزین کنید.
* **پرهیز از حسادت ویژگی (Feature Envy):** یک متد نباید مدام داده‌های داخلی یک کلاس دیگر را دستکاری کند؛ این نشانه آن است که آن متد باید به آن کلاس منتقل شود.
* **قانون دمیتر (Law of Demeter):** از ناوبری‌های ترانزیتی (مثل `a.getB().getC()`) خودداری کنید.
* **کپسوله‌سازی:** شرایط مرزی و شرط‌های پیچیده را در توابعی با نام‌های گویا پنهان کنید. داده‌های پیکربندی را در سطوح بالا نگه دارید و وابستگی‌های منطقی را به وابستگی‌های فیزیکی تبدیل کنید.

## ۳. نام‌گذاری و تست (Naming & Testing)
* **نام‌های گویا:** نام‌ها باید توصیفی، بدون ابهام و آشکارکننده عوارض جانبی (Side Effects) باشند. برای اسکوپ‌های بزرگ از نام‌های طولانی‌تر استفاده کنید. از رمزگذاری‌ها (مثل پیشوند `m_`) پرهیز کرده و اعداد جادویی را با ثابت‌های نام‌دار یا Enum جایگزین کنید.
* **تست‌های جامع:** تست‌ها باید سریع باشند، پوشش کد (Coverage) بالایی داشته باشند و شرایط مرزی را به‌دقت آزمایش کنند. در نزدیکی باگ‌های شناخته‌شده، تست‌های بیشتری بنویسید. یک تست نادیده گرفته‌شده (Ignored Test) نشانه‌ای از ابهام در سیستم است.
* **محیط توسعه (Environment):** فرآیند بیلد و اجرای مجموعه تست‌ها باید در یک مرحله ساده، خودکار و بدون دردسر اجرا شود.

## مثال‌های کد (JavaScript)

```javascript
// ❌ بد: آرگومان پرچمی، حسادت ویژگی، شرط کپسوله‌نشده، اعداد جادویی
function calculatePay(employee, isOvertime) { 
  // G14: حسادت ویژگی (دسترسی مستقیم و دستکاری داده‌های داخلی employee)
  const straightTime = Math.min(400, employee.tenthsWorked);
  const overtime = Math.max(0, employee.tenthsWorked - straightTime);
  
  // G25: اعداد جادویی (400, 1.5)، G16: نیت مبهم
  return straightTime * employee.tenthRate + (isOvertime ? overtime * employee.tenthRate * 1.5 : 0);
}

// G28: شرط کپسوله‌نشده و دشوار برای درک در نگاه اول
if (timer.hasExpired() && !timer.isRecurrent()) {
  deleteTimer(timer);
}


// ✅ تمیز: توابع جداشده، منطق کپسوله‌شده، نام‌های توصیفی، ثابت‌ها
const OVERTIME_MULTIPLIER = 1.5;
const MAX_STRAIGHT_TIME = 400;

function calculateRegularPay(employee) {
  const straightTime = Math.min(MAX_STRAIGHT_TIME, employee.tenthsWorked);
  return straightTime * employee.tenthRate;
}

function calculateOvertimePay(employee) {
  const overtime = Math.max(0, employee.tenthsWorked - MAX_STRAIGHT_TIME);
  return Math.round(overtime * employee.tenthRate * OVERTIME_MULTIPLIER);
}

// G28: شرط کپسوله‌شده، G29: شرط مثبت و خوانا
if (shouldBeDeleted(timer)) {
  deleteTimer(timer);
}

function shouldBeDeleted(timer) {
  return timer.hasExpired() && !timer.isRecurrent();
}
```
