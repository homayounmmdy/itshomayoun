# مدیریت خطا؛ جداسازی مسیر موفقیت از شکست

فصل هفتم کتاب **Clean Code** به نحوه برخورد حرفه‌ای با خطاها می‌پردازد. مدیریت خطا نباید منطق اصلی برنامه (Happy Path) را کثیف، تو در تو یا ناخوانا کند. هدف نهایی، جداسازی شفافِ «کاری که باید انجام شود» از «شرایطی که ممکن است شکست بخورد» است.

در ادامه، مهم‌ترین قوانین مدیریت خطا از دیدگاه رابرت مارتین را مرور می‌کنیم.

## ۱. اصول پایه مدیریت خطا
* **استثناها به جای کدهای بازگشتی (Exceptions Over Return Codes):** استفاده از کدهای بازگشتی (مثل `-1` یا `false`) منطق فراخواننده را با `if`های تو در تو شلوغ می‌کند و به‌راحتی فراموش می‌شود. از `Exception` استفاده کنید تا مدیریت خطا از الگوریتم اصلی جدا شود.
* **اول Try-Catch را بنویسید:** با بلوک‌های `try` مانند یک تراکنش (Transaction) رفتار کنید. ابتدا ساختار `try-catch-finally` را بنویسید تا محدوده و رفتار مورد انتظار در صورت شکست مشخص شود، سپس منطق مسیر موفقیت را درون آن پیاده‌سازی کنید.

## ۲. بهترین روش‌های طراحی استثناها
* **ترجیح استثناهای بررسی‌نشده (Unchecked Exceptions):** استثناهای Checked (مثل جاوا) اصل Open/Closed را نقض می‌کنند، زیرا هر تغییر در آن‌ها نیازمند تغییر امضای متد در تمام طول پشته فراخوانی (Call Stack) است. برای توسعه اپلیکیشن، Unchecked Exceptions گزینه بسیار بهتری هستند.
* **ارائه زمینه (Context):** پیام استثنا باید واضح و اطلاعاتی باشد. دقیقاً مشخص کند کدام عملیات و به چه دلیلی شکست خورده است تا فرآیند دیباگ کردن آسان شود.
* **پوشش‌دهی APIهای شخص ثالث (Wrap Third-Party APIs):** استثناهای خاص کتابخانه‌های خارجی را Catch کنید و یک استثنا سفارشی (Custom Exception) واحد پرتاب کنید. این کار کد شما را از کتابخانه‌های خارجی جدا (Decouple) کرده و وابستگی را کاهش می‌دهد.

## ۳. دشمن شماره یک: Null
* **الگوی مورد خاص (Special Case Pattern):** به جای پرتاب استثنا برای موارد حاشیه‌ای (Edge Cases) که انتظارش را داریم، یک شیء "مورد خاص" (مثلاً یک مقدار پیش‌فرض ایمن) برگردانید تا کد کلاینت تمیز و بدون `if` باقی بماند.
* **هرگز Null برنگردانید:** برگرداندن `null` فراخواننده را مجبور به نوشتن بررسی‌های دفاعی (Null Checks) می‌کند و احتمال خطای زمان اجرا (Runtime Error) را به‌شدت افزایش می‌دهد. به جای آن، یک کالکشن خالی (مثل `[]`) یا یک شیء Special Case برگردانید.
* **هرگز Null پاس ندهید:** پاس دادن `null` به متدها حتی بدتر از برگرداندن آن است! APIهای خود را طوری طراحی کنید که به‌طور پیش‌فرض آرگومان‌های `null` را نپذیرند (مثلاً با استفاده از TypeScript یا اعتبارسنجی در ابتدای متد).

## مثال‌های کد (JavaScript)

```javascript
// ❌ بد: برگرداندن null و مجبور کردن کلاینت به بررسی دفاعی
function getUserPosts(userId) {
  const posts = database.query(userId);
  if (!posts) {
    return null; // کلاینت مجبور است چک کند: if (posts !== null)
  }
  return posts;
}

// ❌ بد: پاس دادن null به متد
function calculateDiscount(price, discountCode) {
  if (discountCode === null) { // بررسی اجباری و زشت
    return price;
  }
  return price - getDiscount(discountCode);
}


// ✅ تمیز: استفاده از الگوی مورد خاص و کالکشن خالی
function getUserPosts(userId) {
  const posts = database.query(userId);
  // همیشه یک آرایه برمی‌گرداند، حتی اگر خالی باشد. کلاینت نیازی به چک کردن null ندارد.
  return posts || []; 
}

// ✅ تمیز: طراحی API که null را نمی‌پذیرد (مثلاً با TypeScript یا پیش‌شرط)
function calculateDiscount(price, discountCode = "NONE") {
  if (discountCode === "NONE") {
    return price;
  }
  return price - getDiscount(discountCode);
}

// ✅ تمیز: الگوی Special Case Object
class NotFoundUser {
  getName() { return "کاربر ناشناس"; }
  isActive() { return false; }
}

function getUser(userId) {
  const user = database.find(userId);
  return user || new NotFoundUser(); // کلاینت با خیال راحت متدها را صدا می‌زند
}
```
