# همروندی؛ شمشیر دو لبه در طراحی نرم‌افزار

فصل سیزدهم کتاب **Clean Code** به یکی از چالش‌برانگیزترین مباحث مهندسی نرم‌افزار می‌پردازد: **همروندی (Concurrency)**. همروندی با جدا کردن «چه کاری» از «زمان انجام آن»، عملکرد و ساختار برنامه را بهبود می‌بخشد، اما ریسک‌های پیچیده‌ای مانند شرایط مسابقه (Race Conditions) و بن‌بست (Deadlocks) را نیز به همراه دارد.

در ادامه، مهم‌ترین اصول دفاعی و بهترین روش‌های مدیریت همروندی از دیدگاه رابرت مارتین را مرور می‌کنیم.

## ۱. اصول دفاعی در برابر آشوب همروندی
* **مسئولیت واحد (Single Responsibility):** کد مربوط به مدیریت نخ‌ها و همروندی را به‌شدت از منطق تجاری (Business Logic) جدا کنید.
* **محدود کردن دامنه داده‌ها:** دسترسی به داده‌های مشترک (Shared Data) را تا حد ممکن محدود و کنترل‌شده نگه دارید.
* **استفاده از کپی‌ها:** به جای به اشتراک‌گذاری وضعیت قابل تغییر (Mutable State)، ترجیحاً از اشیاء کپی‌شده و فقط خواندنی (Read-Only) استفاده کنید.
* **استقلال نخ‌ها (Thread Independence):** نخ‌ها را طوری طراحی کنید که روی زیرمجموعه‌های مستقلی از داده‌ها (مثلاً متغیرهای محلی) کار کنند.

## ۲. بهترین روش‌های اجرایی
* از کالکشن‌های ایمن در برابر نخ (Thread-Safe) و راه‌حل‌های بدون قفل (Non-blocking) استفاده کنید.
* ⚠️ **بخش‌های همگام‌سازی‌شده (Synchronized/Locked) را تا حد ممکن کوچک نگه دارید** تا از افت شدید عملکرد جلوگیری شود.
* از ایجاد وابستگی بین چندین متد همگام‌سازی‌شده روی یک شیء واحد پرهیز کنید.
* خاموش شدن نرم و ایمن (Graceful Shutdown) را از همان ابتدا برنامه‌ریزی کنید، زیرا این فرآیند به‌شدت مستعد ایجاد بن‌بست (Deadlock) است.

## ۳. تست‌نویسی برای کد همروند
* هرگونه شکست تصادفی و نادر را به‌عنوان **باگ همروندی** در نظر بگیرید (افسانه «فقط یک بار اتفاق افتاد» را فراموش کنید).
* ابتدا منطق غیر همروند (اشیاء ساده) را به‌طور کامل و بی‌نقص پیاده‌سازی کنید.
* کد همروند را قابل پیکربندی و تنظیم (Tunable) نگه دارید تا بتوانید تعداد نخ‌ها را به‌راحتی تغییر دهید.
* تست‌ها را با تعداد نخ‌های **بیشتر** از تعداد پردازنده‌ها اجرا کنید تا جابجایی وظایف (Task Swapping) اجباری شده و باگ‌های پنهان آشکار شوند.
* **ابزارسازی کد (Instrumentation):** در حین تست، با تزریق عمدی `sleep`، `yield` یا `wait`، ترتیب اجرای متفاوتی را ایجاد کنید تا شرایط مسابقه (Race Conditions) شکار شوند.

## مثال‌های کد (JavaScript)

```javascript
// ❌ بد: وضعیت مشترک قابل تغییر، بخش بحرانی (Critical Section) بیش از حد بزرگ
let sharedState = { count: 0, data: [] };

function processItem(item) {
  lock(); // قفل خیلی زود گرفته شده است
  sharedState.count++;
  sharedState.data.push(item);
  performHeavyComputation(); // انجام کار سنگین داخل قفل، عملکرد را به‌شدت کاهش می‌دهد
  unlock();
}


// ✅ تمیز: منطق مستقل، استفاده از کپی، بخش بحرانی به حداقل رسیده
function processItemSafely(item) {
  // ۱. استفاده از کپی برای جلوگیری از تغییر مستقیم وضعیت مشترک
  const localData = { ...item }; 
  
  // ۲. انجام کار سنگین و مستقل از نخ، خارج از قفل
  performHeavyComputation(localData); 
  
  // ۳. بخش بحرانی حداقلی: قفل فقط برای به‌روزرسانی کوتاه مشترک
  lock();
  try {
    sharedState.count++;
    sharedState.data.push(localData);
  } finally {
    unlock();
  }
}
```

```javascript
// ✅ تمیز: ابزارسازی (Instrumentation) در تست برای اجبار ایجاد Race Condition
class ThreadSafeQueue {
  constructor() {
    this.items = [];
  }

  async push(item) {
    // ابزارسازی: تسلیم عمدی اجرا (yield) برای اجبار جابجایی نخ‌ها 
    // و آشکار کردن Race Conditionهای پنهان در حین تست.
    await testJiggle(); 
    
    lock();
    try {
      this.items.push(item);
    } finally {
      unlock();
    }
  }
}

// ابزارسازی فقط مخصوص محیط تست
async function testJiggle() {
  if (process.env.NODE_ENV === 'test') {
    // خواب یا yield تصادفی برای ایجاد مسیرهای اجرایی غیرقابل پیش‌بینی
    await new Promise(resolve => setTimeout(resolve, Math.random() * 10)); 
  }
}
```
