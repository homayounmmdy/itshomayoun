# کلاس‌ها؛ بلوک‌های سازنده سیستم

فصل دهم کتاب **Clean Code** به یکی از بنیادی‌ترین مفاهیم طراحی نرم‌افزار، یعنی **کلاس‌ها (Classes)** می‌پردازد. رابرت مارتین تأکید می‌کند که اندازه یک کلاس نه با تعداد خطوط کد، بلکه با **تعداد مسئولیت‌هایش** سنجیده می‌شود. یک کلاس خوب، کلاسی است که تمرکز بالایی داشته باشد و به‌راحتی قابل درک و تغییر باشد.

در ادامه، مهم‌ترین اصول طراحی و سازماندهی کلاس‌ها را مرور می‌کنیم.

## ۱. اندازه و سازماندهی (Size & Organization)
* **کوچک بودن:** نام کلاس باید مختصر و گویا باشد (از پسوندهای مبهم مثل `Manager`، `Processor` یا `Super` پرهیز کنید). باید بتوانید رفتار کلاس را در حدود ۲۵ کلمه و **بدون** استفاده از کلماتی مثل «و»، «اگر»، «یا» یا «اما» توصیف کنید.
* **سازماندهی اعضا:** اعضای کلاس را به‌صورت منطقی و از بالا به پایین مرتب کنید: 
  1. ثابت‌های عمومی استاتیک (Public static constants)
  2. متغیرهای خصوصی استاتیک (Private static variables)
  3. متغیرهای نمونه خصوصی (Private instance variables)
  4. متدهای عمومی (Public methods)
  5. متدهای کمکی خصوصی (Private utility methods)
  *(این ترتیب، پیروی از قانون سرازیری یا Stepdown Rule است).*

## ۲. اصول SOLID در طراحی کلاس
* **اصل مسئولیت واحد (SRP):** یک کلاس باید **یک و فقط یک** دلیل برای تغییر داشته باشد. اگر کلاسی هم کار رابط کاربری انجام می‌دهد و هم منطق دیتابیس، مسئولیت‌های متمایز را به کلاس‌های جداگانه و قابل استفاده مجدد استخراج کنید.
* **انسجام (Cohesion):** یک کلاس باید تعداد کمی متغیر نمونه داشته باشد و متدهای آن باید با **همه یا اکثر** این متغیرها کار کنند. اگر متدهای مختلف فقط زیرمجموعه‌های جداگانه‌ای از متغیرها را استفاده می‌کنند، کلاس فاقد انسجام است و باید شکسته (Split) شود.
* **اصل باز-بسته (OCP):** کلاس‌ها باید برای توسعه (مثلاً از طریق ارث‌بری یا پیاده‌سازی اینترفیس) **باز**، اما برای تغییر کد داخلی **بسته** باشند. این کار از شکستن (Break) کد موجود هنگام افزودن قابلیت‌های جدید جلوگیری می‌کند.
* **اصل وارونگی وابستگی (DIP):** به جای وابستگی به جزئیات پیاده‌سازی (کلاس‌های مشخص و Concrete)، به **انتزاعات (رابط‌ها/اینترفیس‌ها)** وابسته باشید. این کار سیستم را از تغییرات خارجی ایزوله کرده و تست‌نویسی را با استفاده از Mock یا Stub بسیار آسان می‌کند.

## مثال‌های کد (JavaScript)

```javascript
// ❌ بد: کلاس خدا (God Class)، نقض SRP، انسجام پایین، وابستگی‌های مشخص (Concrete)
class SuperDashboardManager {
  constructor() {
    this.version = "1.0";
    this.uiElement = document.getElementById("app");
    this.db = new ConcreteDatabase(); // نقض DIP: وابستگی سخت‌کد شده به یک کلاس مشخص
  }

  updateVersion() { this.version = "1.1"; } // دلیل تغییر ۱: مدیریت نسخه
  renderUI() { this.uiElement.innerHTML = "Hello"; } // دلیل تغییر ۲: رابط کاربری
  saveData(data) { this.db.save(data); } // دلیل تغییر ۳: دیتابیس
}


// ✅ تمیز: رعایت SRP، انسجام بالا، OCP و DIP

// ۱. SRP و انسجام: مسئولیت‌های ایزوله و مستقل
class Version {
  constructor(major, minor) {
    this.major = major;
    this.minor = minor;
  }
  getFullVersion() { return `${this.major}.${this.minor}`; }
}

// ۲. DIP: وابستگی به یک انتزاع (مفهوم اینترفیس)
class Database {
  save(data) { throw new Error("Method must be implemented"); }
}

// به‌راحتی قابل تست و جایگزینی است (رعایت OCP)
class MockDatabase extends Database {
  save(data) { console.log("Saved to mock:", data); }
}

// ۳. DIP و OCP: تزریق وابستگی (Dependency Injection)، بسته برای تغییر، باز برای توسعه
class Dashboard {
  constructor(database) { // تزریق انتزاع به جای ساختن آن در داخل کلاس
    this.db = database;
    this.version = new Version(1, 0);
  }

  render() { /* فقط منطق رابط کاربری */ }
  
  saveData(data) { 
    this.db.save(data); 
  }
}
```
